## Задача 1. Сумма чисел от 1 до N: threading vs multiprocessing vs async

Файлы: [`task1/sum_threading.py`](task1/sum_threading.py),
[`task1/sum_multiprocessing.py`](task1/sum_multiprocessing.py),
[`task1/sum_async.py`](task1/sum_async.py).

Каждая программа содержит функцию `calculate_sum(n, workers)`, которая
делит диапазон `1..n` на `workers` равных кусков и суммирует их
параллельно (потоками / процессами / корутинами), затем складывает
частичные суммы.

По заданию N = 10 000 000 000 000 (10¹³). Реальный прогон с таким N на
чистом Python занимал бы часы вне зависимости от подхода (см.
экстраполяцию ниже), поэтому для измерений и сравнения подходов N был
уменьшен — корректность при этом проверяется точной формулой
`n(n+1)/2`, поведение (какой подход быстрее и почему) от N не зависит.
Полное N=10¹³ можно передать флагом `--n`, если нужно запустить «как в
задании» (это просто займёт много времени).

Запуск:

```bash
cd lab2/task1
python3 sum_threading.py --n 500000000 --workers 8
python3 sum_multiprocessing.py --n 500000000 --workers 8
python3 sum_async.py --n 500000000 --workers 8
```

### Результаты измерений (N = 500 000 000, 8 воркеров, MacBook, 8 ядер)

| Подход           | Время выполнения | Загрузка CPU | Сумма (проверена формулой) |
|------------------|------------------:|-------------:|:---------------------------|
| threading        | 4.91 сек          | ~100% (1 ядро) | 125000000250000000 ✅ |
| multiprocessing  | 1.12 сек          | ~685% (≈7 ядер) | 125000000250000000 ✅ |
| async / asyncio  | 4.93 сек          | ~100% (1 ядро) | 125000000250000000 ✅ |

Корректность на малом N (N = 10 000 000): все три программы дают
`50000005000000`, что совпадает с `n(n+1)/2`.

**Экстраполяция на N = 10¹³** (линейно, ×20000 от замера): threading и
async — около **27 часов**, multiprocessing — около **6 часов**. Именно
поэтому полный прогон по заданию непрактичен на одной машине.

### Комментарий к результатам

* **threading** не ускоряет CPU-bound код: из-за GIL (Global Interpreter
  Lock) в CPython только один поток исполняет байткод в любой момент
  времени. Все 8 потоков соревнуются за GIL, поэтому время ≈ как у
  одного потока, а CPU загружен на одно ядро.
* **multiprocessing** даёт реальное ускорение (~4.4×), потому что у
  каждого процесса свой интерпретатор и свой GIL — вычисления реально
  выполняются параллельно на разных ядрах. Ускорение не строго ×8
  из-за накладных расходов на старт процессов и передачу результатов
  между процессами.
* **async/asyncio** — это кооперативная многозадачность в одном
  потоке: `await asyncio.sleep(0)` лишь передаёт управление другой
  корутине, но пока одна корутина считает — все остальные ждут. Для
  CPU-bound задач asyncio не даёт выигрыша (как и threading), в чём и
  заключается его отличие от I/O-bound сценария (см. Задачу 2).

## Задача 2. Параллельный парсинг веб-страниц с сохранением в БД

Файлы: [`task2/db.py`](task2/db.py) (модель БД), [`task2/urls.py`](task2/urls.py)
(список URL), [`task2/parse_threading.py`](task2/parse_threading.py),
[`task2/parse_multiprocessing.py`](task2/parse_multiprocessing.py),
[`task2/parse_async.py`](task2/parse_async.py).

Каждая программа содержит функцию `parse_and_save(url)`, которая
загружает HTML-страницу, парсит из неё `<title>` (через
`BeautifulSoup`), сохраняет `(url, title, approach, parsed_at)` в базу
данных и выводит результат на экран.

### База данных

Используется база данных лабораторной работы №1
(`bookcrossing.db`, подключение из `bookcrossing/.env` → `DB_ADMIN`).
Существующие таблицы буккроссинга (`user`, `book`, `genre`, ...)
предметно не связаны с текстом произвольных веб-страниц, поэтому вместо
попытки притянуть парсинг к ним заведена новая таблица **`parsed_page`**
в той же базе (создаётся автоматически при первом запуске любого из
скриптов через `init_db()` в [`task2/db.py`](task2/db.py)):

| Поле        | Тип      | Описание                          |
|-------------|----------|------------------------------------|
| `id`        | int, PK  | автоинкремент                     |
| `url`       | str      | адрес страницы                    |
| `title`     | str      | содержимое `<title>`              |
| `approach`  | str      | `threading` / `multiprocessing` / `async` |
| `parsed_at` | datetime | момент сохранения (UTC)           |

Каждый поток/процесс/корутина открывает **своё** соединение с БД
(`get_engine()` вызывается заново на каждый вызов `parse_and_save`),
чтобы не делить одно соединение SQLite между потоками/процессами.

### Список URL (`task2/urls.py`)

`example.com`, `python.org`, `docs.python.org/3`, `wikipedia.org`,
`iana.org/domains/reserved`, `httpbin.org`, `w3.org` — 7 публичных
страниц с разным временем ответа. Как и требует задание, список делится
на равные части между воркерами (`urls.split_into_chunks`): каждый
поток/процесс/корутина получает свой кусок списка и обрабатывает URL из
него последовательно через `parse_and_save(url)`.

Запуск:

```bash
cd lab2/task2
python3 parse_threading.py --workers 3
python3 parse_multiprocessing.py --workers 3
python3 parse_async.py --workers 3
```

### Результаты измерений (7 URL, 3 воркера)

| Подход           | Время выполнения | Все 7 заголовков сохранены |
|------------------|------------------:|:---------------------------|
| threading        | 3.37 сек          | ✅ |
| multiprocessing  | 3.35 сек          | ✅ |
| async / aiohttp  | 2.99 сек          | ✅ |

### Комментарий к результатам

Парсинг страниц — задача **I/O-bound**: большую часть времени программа
не считает, а ждёт ответ от сервера по сети. В этом сценарии картина
обратная Задаче 1:

* **threading** здесь реально ускоряет работу: во время ожидания
  ответа сети GIL освобождается, и другой поток может в это время
  отправить свой запрос. 7 запросов выполняются практически
  одновременно, а не последовательно.
* **multiprocessing** тоже параллелит запросы, но каждый процесс — это
  отдельный интерпретатор Python (с накладными расходами на старт и
  сериализацию), что для лёгких I/O-задач не даёт преимущества перед
  threading, а часто немного медленнее из-за overhead на создание
  процессов.
* **async/aiohttp** оказался самым быстрым: один поток, один процесс,
  но `aiohttp` асинхронно инициирует все запросы почти одновременно и
  просто переключается между ними, пока не придут ответы — без затрат
  на создание потоков/процессов ОС.

**Вывод по обеим задачам:** для CPU-bound кода нужен `multiprocessing`
(обход GIL реальными процессами); для I/O-bound кода (сеть, диск,
внешние API) `threading` и особенно `async/asyncio` выигрывают за счёт
дешёвого переключения задач во время ожидания, при этом `asyncio`
обычно эффективнее по накладным расходам, чем потоки ОС.
